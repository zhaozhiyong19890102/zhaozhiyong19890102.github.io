1. RAG大模型的架构

传统方法输入后LLM直接生成答案并返回给用户

加入RAG后，先对documents进行indexing（产生了怎么分块，每块与Query的相似度有多少，怎么得到embedding等问题），之后Query与embeddings进行相似度计算即Retrieval得到Relevant Documents，再与Query拼接作为输入给LLM，最终呈现Answers。

2. RAG核心步骤

2.1. Indexing（索引）

  1. 数据提取：
    • 数据清洗：数据loader，提取pdf、word、markdown以及数据库和AGI等；
    • 数据处理：数据格式处理，不可识别内容的剔除，压缩和格式化等；
    • 元数据提取：提取文件名、时间、章节title等信息。
  2. 分块：
    • 固定大小的分块方式:一般是256/512个tokens，取决于embedding模型的情况。但是这种方式的弊端是会损失语义
    • 基于意图的分块方式:句分割–最简单的是通过句号和换行来做切分。当然也有通过专业的意图包来切分的，常用的意图包有基于NLP的NLTK和spaCy
    • 较为简单的方式是检索句号，如果检索到句号且小于256个tokens，继续检索，当检索到句号已经达到256个tokens时，将最后一句放在下一个chunk的首句。
  3. 影响分块策略的因素：
    • 取决于你的索引类型，包括文本类型和长度，文章和微博推文的分块
    • 模型类型，tokens限制长度不一样
    • 问答的文本的长度和复杂度:最好问答的文本长度和你分块的尺寸差不多，这样会对检索效率更友好
  4. 向量化
    • 将文本、图像、音频和视频等转化为向量矩阵的过程，也就是变成计算机可以理解的格式，更方便计算相似度、距离等
    • embedding模型的好坏会直接影响到后面检索的质量，特别是相关度
    • 向量化方法：
      • BGE：这是国人开发的中文embedding模型，在HuggingFace的MTEB(海量文本Embedding基准)上排名前2。支持超过一百种语言，并且能够高效实现不同细粒度的检索任务
      • M3E：也是国人开发的中英双语embedding模型，Moka Massive Mixed Embedding。主要针对中文文本进行向量化处理，但也有一定的双语处理
      • 基于PLM的,如Sentence-t5等，直接通过huggingface调用，计算词向量

2.2. Retrieval（检索）：

  1. 预处理：
    • 元数据过滤：当我们把索引分成许多chunks的时候，检索效率会成为问题。这时候，如果可以通过元数据先进行过滤，就会大大提升效率，比如寻问帮我对第二季度中，公司在服装方面带来的营收进行统计。如果有元数据，比如“第二季度 服装 营收”，那么检索量就会大大降低
    • 图关系检索：如果可以将很多实体变成node，把它们之间的关系变成relation，就可以利用知识之间的关系做更准确的回答，尤其适合多跳
    • 检索方法：
      • 相似度检索：包括欧氏距离、曼哈顿距离、余弦等
      • 关键词检索 ：先把chunk做摘要，再通过关键词检索找到可能相关的chunk，一般时间复杂度是O（n²）
      • SQL检索：把query转为SQL语句
    • 重排序、迭代、自省等等

2.3. Generation（生成）：

组装prompt——提出的查询和选定的文档被渲染成一个提示（Prompt），输入到模型之中生成答案

3. 关键技术和方法介绍

3.1. Native RAG

包括最基本的Indexing-Retrieval-Generation三个过程

  • 不足：效果不好
    • 准确性低：Retrieval阶段查询到的块，和query本身的相关性低（Retrieval得到的Documents可能本身相关性不大，即使取出TOP-K相关性也不大，反而产生噪音，可能导致LLM出现幻觉）。
    • 召回低：Retrieval阶段查询的块，并没有返回足够多的相关块
    • 组装prompt的问题：这个阶段会将检索到的块和query融合，若检索到的多个块中包含了相似或重复的内容，可能导致最终LLM生成内容的冗余和重复
    • 过度依赖：生成模型可能过度依赖增强的信息，导致输出只是回应检索到的内容，而不添加有见地或合成的信息

3.2. Advanced RAG

采用了预检索和后检索策略（pre-retrieval and post-retrieval strategies）

3.2.1. 预检索——重点在于优化索引结构和原始查询

1、优化索引

目标是提高被索引内容的质量。这涉及五种主要策略：增强数据粒度、优化索引结构、添加元数据、对齐优化和混合检索。

增强数据粒度：

粗粒度：例如文档分块chunk较大。理论上粗粒度，能包含更多的相关信息。

细粒度：例如文档分块chunk较小。细粒度会导致分块很多，可能避免用一些冗余信息。

动态优化，自适应进行chunk的切分

滑动窗口

添加元数据

例如chunk的元数据：页码、文件名、作者、时间、类别（用Query中关键的token与chunk中元数据做比对来筛选）

检索时可通过meta data先过滤，例如检索time range内的chunk

2、优化查询

目标是让用户的原始问题更清晰，更适合于检索任务。

常见的方法包括查询改写、查询转换、查询扩展等

查询扩展：

将单个查询扩展为多个查询，丰富查询内容，可提供更丰富的上下文信息（由于chunk的长度要与Query差不多，如果Query过小，会加大检索成本，所以可以进行增加改写）

将复杂问题拆分成多个子问题，也会增加chunk长度，降低检索成本

查询转换

让LLM优化原始query

使用专门的较小的语言模型进行改写（Rephrasing）

让LLM先生成原始query的答案，然后将答案作为query，去根据相似性检索（而不是直接用原始query去检索）

后检索——重点是有效的融合检索到的相关内容和query（重排，总结，融合等）

1、分块chunk重排序

将检索到的块里，最相关的块优先级提高（用什么方法计算相关性很重要）

2、上下文压缩

一个是避免prompt超长，超过LLM的窗口限制

另一个是找到基础信息，强调关键信息，将不相关的内容压缩、精简、淡化（如通过摘要生成的方法获取关键信息，用一个已经训练好摘要生成方法的小模型或一个用自己数据微调过的摘要生成的小模型或一个大模型或将大模型的task description加入一些与任务相关的描述）

Modular RAG
Modular RAG 引入多个特定功能模块和替换现有模块， 总体上展示了更大的灵活性。其过程并不局限于顺序检索和生成，包括了迭代和自适应检索。

advancedRAG 阶段主要解决的问题是「检索什么内容」，modularRAG 需要解决「什么时候检索」的问题。以下介绍三种循环检索 - 生成的方式：

IterativeRAG

先用原始 query 检索生成，然后将生成结果 + 原始 query 进行第二轮检索生成，N 次迭代或 llm 判断可以回答问题后停止。

IterativeRAG实例
AdaptiveRAG

FLARE：模型生成低置信度 token 时停止生成或者regenerate，或者用 prompt 指示模型不确定时停止生成。

FLARE
Self-RAG

当模型认为需要检索，生成特殊的 token。

此时根据问题进行常规检索。并且分开检索。

用模型对生成结果进行自我评判，将选择的最优生成结果作为 context 继续生成。

RAG大模型与传统模型的比较
工作原理：
RAG模型：RAG结合了检索（Retrieval）和生成（Generation）的能力。

传统模型：传统的自然语言处理模型（如GPT-3或BERT）依赖于预先训练好的模型参数来生成回答。

知识动态更新：
RAG模型：因为RAG可以从外部数据源实时检索信息，理论上可以保持知识的最新性

传统模型：传统模型在训练结束后，模型内部的知识就固定了，不能动态更新

计算资源：
RAG模型：检索能够减少模型需要记忆的知识量，从而提升生成效果。

传统模型：在训练过程中，如果模型需要学习大量知识，训练成本可能非常高

RAG，Fine tuning与Prompt Engineering在模型泛化性与外部知识要求的对比
